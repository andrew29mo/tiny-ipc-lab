# Related systems, failure modes and useful next experiments

Primary sources consulted on 2026-10-15. These are design references, not competing systems installed or benchmarked here. Their features and published results do not validate this project or imply equivalent functionality.

| Reference | Relevant lesson | Application here |
|---|---|---|
| [Ray object serialization](https://docs.ray.io/en/latest/ray-core/objects/serialization.html) | Shared NumPy objects can be read without deserialization copies on the same node; immutability supports sharing. Writes require a private copy. | The shared consumer now has a read-only NumPy view. This is an API guard, not OS permission or tenant isolation. The producer still copies its input into the slot, so this is not a fully zero-copy pipeline. |
| [Ray memory management](https://docs.ray.io/en/latest/ray-core/scheduling/memory-management.html) | Per-worker RSS can include the same shared pages repeatedly; worker heap, object-store capacity and resident physical accounting differ. | Preserve paired process RSS and sampling gaps; do not call it deduplicated physical memory or infer a percentage saving from separate maxima. Linux PSS/USS or platform-specific physical accounting would be a separate measurement. |
| [iceoryx delivery example](https://iceoryx.io/classic/v2.0.0/examples/icedelivery/) | Loaning a shared sample, constructing it in place and releasing ownership are central to avoiding copies safely. | This MVP conservatively waits for an ACK before reuse. A future in-place producer API could remove the source-to-slot copy, but would need a new comparison against an equally changed workload. |
| [iceoryx slow-subscriber discussion](https://github.com/eclipse-iceoryx/iceoryx/issues/615) | A full consumer queue requires a deliberate block/drop policy; waiting and shutdown can interact. This is a historical design discussion, not evidence of an unresolved current defect. | A future multi-slot ring must specify full-buffer behavior, consumer-held lifetimes, cancellation and shutdown. More slots do not automatically guarantee better latency or safe reuse. |
| [iceoryx2 cleanup FAQ](https://github.com/eclipse-iceoryx/iceoryx2/blob/main/FAQ.md) | Cleanup depends on ownership, surviving participants, access rights and the kind of stored data. | One controller owns unlink, with actual worker-crash and partial-result tests. Killing that controller or the whole machine remains outside the guarantee. |
| [CPython Connection source](https://github.com/python/cpython/blob/v3.12.14/Lib/multiprocessing/connection.py) | A receive-into API can still allocate an intermediate buffer. Preallocation at the caller is not enough to establish allocation-free transport. | Keep recv_bytes_into as the original baseline and add recv_bytes plus target copy as a public-API sensitivity comparison. The RSS diagnosis controls the allocator separately. |

## What is worth building next

1. **Allocation-aware IPC diagnosis.** Make the distinction between live allocations, allocator-retained pages and shared-page accounting easy to inspect. The retained diagnosis is a concrete start; automatic leak classification would need longer, cross-platform evidence.
2. **Explicitly loaned bounded buffers.** Add a small multi-slot pool with sequence/generation tokens, a defined full policy and an in-place producer. Test slow/crashed consumers and stale acknowledgements before considering lock-free synchronization. This is proposed work, not functionality claimed by the current single-slot protocol.
3. **Separate transport and application-work profiles.** Keep complete verified round trips, but add a clearly labeled transport-focused workload with independent correctness validation and explicit validation cost. Do not subtract two noisy timings to invent a transport speedup.
4. **A direct receive-into socket control.** A local socket recv_into loop can investigate the cost of intermediate receive buffers. It needs exact framing, short-read handling, EOF/deadline tests and identical capacity; it is not implemented or measured in this revision.

The useful differentiation is an inspectable ownership and measurement contract, with evidence that also explains disappointing or surprising results. Shared memory, ACK-based ownership and zero-copy designs are established techniques; this project does not claim to invent them.
